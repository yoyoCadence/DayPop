## 3. 發現

### 3.1 子項在列表、寵物徽章與綜覽被當成獨立待辦 —— 中（DP-121）

**來源**：#106 讓使用者可以直接建立子項；底層的平鋪儲存早已存在，但在此之前只有匯入會產生子項，所以幾乎碰不到。

**原稿行為**：子項存在父待辦裡面（`t.subs`，`.dc.html:1149-1152`）。列表只取 `state.todos`（`:690`），寵物徽章是 `state.todos` 中今天或之前、尚未完成的數量（`:1304-1306`），所以只會計入最上層待辦。

**DayPop 現況**：子項是帶 `parentId` 的獨立 `TodoItem`，以下三處都沒有過濾：

| 位置 | 行為 |
| --- | --- |
| `src/screens/calendar/AgendaView.tsx:143` | 列表檢視把當天每一筆待辦平鋪成一列。 |
| `src/screens/calendar/CalendarScreen.tsx:263` | `openTodoCount`（寵物徽章）計入子項。 |
| `src/screens/OverviewScreen.tsx:81` | 綜覽把 `data.todos` 全部交給分組。 |

**重現**（dev server、390×844、`Asia/Taipei`）：預先寫入一筆今天的父待辦與兩個子項的 schema v4 遊客文件，打開列表檢視。

- 畫面顯示 3 筆並列的「待辦」。
- 寵物徽章顯示 `3`。
- 依原稿應為 1 筆、徽章 `1`。
- console 0 error／warning。

綜覽只讀了程式碼，沒有在畫面上確認。

**建議修法**：這三處只取 `parentId === null` 的待辦，或取「父項不在同一份資料裡」的待辦，與 `src/domain/todos.ts` 的 `todoGroupsOn()` 判定一致。日詳情已經會把子項收在父項之下，不需要改。

**驗收條件**：

- 有子項時，列表、徽章與綜覽都只計最上層。
- 父項不存在的孤兒子項（例如匯入資料）仍然看得到。
- 加上單元與 e2e 回歸。

### 3.2 0.4.2 公告漏列 #108 與 #110 —— 發布前必須處理（DP-122）

**來源**：#107 在 `d253696` 寫好 0.4.2 公告，之後 #108（資料與隱私說明）與 #110（待辦改名）才合併，兩項都是使用者看得到的功能，但不在 `release-notes.json` 的 0.4.2 條目裡。

**現況**：0.4.2 尚未部署（2026-10-04 線上 `version.json` 為 0.4.1），所以依規則仍可修改。

**限制**：0.4.2 的 8 條公告在 0.3.0 的不可捲動對話框裡已超出 9px（見 3.3）。再多一行，按鈕就會被推出畫面。

- 改完重新用真實 0.3.0 build 量測（方法見 3.3）。
- 部署時 DP-110 的檢查會比對線上 0.4.1，不受影響。

### 3.3 #107 沒有用 0.3.0 對話框量公告長度 —— 低（併入 DP-122）

**規則**：AGENTS.md §0.1 規定，只要還有使用者可能停在 0.3.0，公告就必須在 0.3.0 的 CSS 下、375×667 直向與 932×430 橫向都放得下。#107 的描述與 `docs/deployment.md` §5.18 只量了 0.4.2 自己的公告畫面（可捲動），沒有量 0.3.0。

3. 在 mobile Chromium 量對話框與兩顆按鈕。
4. 0.4.0 公告作為校準，它在橫向量到 `15..418/430`，與 DP-089 的紀錄相同。

**0.4.2 的結果**：

### 3.4 遊客模式的待辦輸入錯誤顯示「資料尚未同步」—— 低（DP-123）

**來源**：#106 在 `src/data/DataProvider.tsx:236` 把 `TodoInputError` 併進原本處理 `RemoteDataError` 的分支，產生 `kind: 'write-failed'` 的 warning；`src/shell/RemoteDataWarningBanner.tsx:27` 對它顯示「資料尚未同步」。#110 的改名也會走到這裡。

**影響**：遊客不會同步，這個標題不正確。觸發條件是在刪除父項或待辦之後、畫面更新之前送出子項或改名，實際很難碰到；下一次寫入成功時 warning 就會清除。

**建議**：讓輸入錯誤使用不提「同步」的訊息，或依 session 是否為帳號決定標題。

### 3.5 DP-110 的紀錄已過時 —— 低（DP-124）

`tasks.md` 的 DP-110 Done 條目、DP-034 的 DP-110 子項進度，以及 `docs/deployment.md` §5.17 都寫著部署 workflow 的公告檢查「還沒在 runner 上實際跑過」。實際上 2026-10-03 部署 0.4.1 時（run `37132293407`，head `d713b52`）已經執行並通過，log 為 `Release notes check passed: 0.4.1 replaces 0.4.0, whose notes are unchanged.`。

`deploy-staging.yml` 的註解寫的是「在加入當下」，仍然正確。

### 3.6 標題 300 字上限只有資料庫在擋 —— 既有問題、低（DP-125）

`todos` 與 `events` 的 title 在資料庫有 1–300 字的 CHECK，但 domain validation 只要求「非空且已 trim」，前端輸入框也沒有 `maxLength`。

- 遊客可以存超過 300 字的標題，同樣內容在登入帳號會寫入失敗。
- 這不是本批 PR 引入的；#110 的改名框（`src/screens/calendar/EditableTodoTitle.tsx:69`）同樣沒有限制，讓它更容易碰到。

**建議**：在 domain 與輸入框都限制 300 字，並決定遊客既有的超長資料如何處理。
