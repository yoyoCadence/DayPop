## 2. 發現的問題

### 2.1 頁面畫布的底色是寫死的紫，永遠不隨主題變（中）→ DP-074

狀態列那一段有一條 **`#f7f3ff` 淡紫色帶**，切換到深色主題也不變。iOS Safari 與加到主畫面兩種模式表現相同。

以 Playwright 對線上 staging 量測（430×932、DPR 3、`zh-TW`／`Asia/Taipei`），四個分頁 × 淺／深色：

| 層 | 淺色 | 深色 |
| --- | --- | --- |
| `html`（畫布） | `rgb(247,243,255)` | `rgb(247,243,255)` ← **沒變** |
| `.dp-preview` | `rgb(255,255,255)` | `rgb(18,18,18)` |
| `.dp-viewport` | `rgb(255,255,255)` | `rgb(18,18,18)` |
| `.dp-screen`（作用中分頁） | `rgb(255,255,255)` | `rgb(18,18,18)` |
| `theme-color` meta | `#ffffff` | `#121212` |

App 自己的三層背景與 `theme-color` **全部正確**，壞的只有畫布這一層。

**根因是 specificity，不是載入順序。** 根元素上有三條背景規則同時存在：

| 來源 | 選擇器 | 值 |
| --- | --- | --- |
| `shell.css` 20–24 | `html` | `#0a0a0c`（**本來想要的**） |
| `styles.css` 1–3 | `:root` | `#f7f3ff` |
| `styles.css` 26–31 | `html` | 漸層 ＋ `#f7f3ff` |

`:root` 的 specificity 是 `(0,1,0)`、`html` 是 `(0,0,1)`，所以 **`:root` 恆勝，`shell.css` 那條是死碼**。它上面那句註解「App viewport 會自己畫主題背景」只在 `.dp-preview` 的盒子範圍內成立，盒子外的畫布是 canonical 搬移前 scaffold 樣式表的紫。

**成因未確認的部分**：畫布為什麼會在安全區那一段露出來，**這一輪沒有查清楚，不得寫成已確認**。模擬環境重現不了 —— Chromium 的 `env(safe-area-inset-*)` 恆為 `0px`，沒有那段區域可看。最合理的機制是 `overscroll-behavior: none` 只下在 `body`、`html` 算出來是 `auto`（`shell.css` 28–33），iOS 的橡皮筋回彈因此露出畫布，但這是**假設，沒有證據**。

**修法不依賴知道機制**：只要畫布顏色接上主題，不管從哪條路徑露出來，露出的都會是主題色。

**過程中被證偽的一個假設，留著避免下一輪重走**：原本以為差異出在 `.cal-screen { overflow: hidden }`（`calendar.css` 9–13）讓日曆分頁不是捲動容器。**那條規則其實沒有生效** —— `.dp-screen { overflow-y: auto }`（`shell.css` 97–105）同 specificity 但在後面載入，日曆分頁算出來也是 `auto`。只讀原始碼會得到相反結論，必須看計算值。這條 dead rule 目前沒有可見症狀（`.cal-screen` 的 `scrollHeight` 等於 `clientHeight`），但屬同一類遺留，已一併記進 DP-074。

### 2.2 快速新增不吃中文數字的時間（中）→ DP-075（產品決策）

真機打「`明天下午三點 開會`」建出的是**全天**事件，標題還留著「三點 開會」。

以專案 vitest 直接餵 `parseQuickAdd()` 確認（`now = 2026-08-22T12:00:00+08:00`）：

| 輸入 | 標題 | 全天 | 開始 |
| --- | --- | --- | --- |
| `明天下午3點 開會` | `開會` | 否 | 15:00 |
| `明天下午三點 開會` | `三點 開會` | **是** | 09:00 |
| `明天下午十點 開會` | `十點 開會` | **是** | 09:00 |
| `明天15點 開會` | `開會` | 否 | 15:00 |
| `明天下午3:00 開會` | `開會` | 否 | 15:00 |
| `明天下午3點 開會 @會議室A 提前15分` | `開會`（地點 `會議室A`、提前 15 分） | 否 | 15:00 |

根因是時間正則 `(\d{1,2})\s*[:：點点時时]\s*(\d{1,2})?`（`quickAdd.ts:122`）的 `\d` 只吃 ASCII 數字：比對不到 → `hour` 留在 `null` → `allDay = hour === null`（`quickAdd.ts:138`）判成全天，而「三點」沒被時間規則吃掉就留在標題裡。兩個症狀同一個根因。

**這是忠實移植，不是搬移時弄壞的。** 原檔 `.dc.html:974` 是逐字相同的正則、`:979` 是逐字相同的 `allDay = hh==null`。依專案規則（同 DP-015／DP-064／DP-070）另立任務，不在 QA 分支改。

**週檢視看不到這筆事件是正確行為**，不是第二個 bug —— 原稿 `buildWeek()` 的 `evs.forEach(e=>{ if(e.allDay) return; ... })` 本來就略過全天事件，DayPop 的 `WeekView.tsx` 保留同樣行為，tasks.md 的 DP-014 條目已記。

### 2.3 只給時間時標題是空的，儲存會靜默失效（中）→ DP-076（偏離原稿）

比對原稿時順帶量到的，不是真機操作發現的。

`明天下午3點`、`明天`、`下午3點` 三種輸入，`parseQuickAdd()` 回傳的 `title` 都是 `""`。原檔是 `const title = str.trim() || '新事件';`（`.dc.html:983`），`quickAdd.ts:142` 沒有那個 fallback —— 與 §2.2 相反，這一條是**搬移缺口**，原稿才是 canonical。

實際症狀比「少一個預設字串」嚴重：DP-060 之後快速新增交由事件 sheet 確認建立，而 `EventSheet.tsx:162` 的 `if (!title.trim()) return;` 是**沒有任何訊息的 early return**，使用者按儲存會什麼都不發生也得不到解釋。
